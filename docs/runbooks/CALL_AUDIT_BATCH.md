# Call Audit one-shot batch runbook

Operator procedure for `npm run callaudit:batch` (`src/cli/run-call-audit-batch.ts`).

This command is **one-shot**: no scheduler, cron cadence, watch mode, poll loop,
or retry loop. It performs one bounded run over one operator-supplied period and
exits with a code. Running it again is a new deliberate act. Call Audit is
separate from Billing Audit: nothing here reads, derives, or reports a
chargeable figure, and no step changes billing.

## Current posture — read first

- Migration `0008_call_audit_foundation.sql` is **not applied in production**.
- This runbook covers a **staging / shadow** run under named, approved
  supervision. It neither authorizes production use nor asserts production is
  approved.
- `ai_voice_leads_received` is **external and read-only**. The source reader
  issues `SELECT` only; nothing writes, alters, locks, or foreign-keys to it.

## Prerequisites

All must be true and evidenced before arming a run:

1. Backup/restore evidence for the target (staging) database reviewed by the
   named data owner.
2. `0008_call_audit_foundation.sql` applied to staging, schema verified.
3. **Least-privilege** MySQL account: no DDL, no rights on the source table
   beyond `SELECT`, writes limited to the `kaudit_call_audit_*` tables.
4. MySQL TLS configured (CA mounted; the CLI sets `rejectUnauthorized`).
5. `OPENAI_API_KEY` injected from the secret manager — never in a repository
   file, shell history, ticket, or log.
6. Exactly one rule version **active**, created and validated by an
   administrator. The CLI audits under whatever is active and invents no prompt,
   model, or temperature; with none active it stops with
   `CALL_AUDIT_BATCH_NO_ACTIVE_RULE` before any spend.
7. A named operator owns the run and is present throughout.
8. Model spend for the intended candidate count approved in advance.

## The arming gate

`KAUDIT_CALL_AUDIT_BATCH_MODE` must be **byte-exact** `EXECUTE` — compared
without trimming and without case folding. `execute`, `Execute`, `EXECUTE `
(trailing space), ` EXECUTE`, `true`, or unset all refuse with
`CALL_AUDIT_BATCH_MODE_NOT_EXECUTE`. The gate is evaluated first, so a refusal
happens **before** runtime config is loaded, the pool is created,
`OPENAI_API_KEY` is read, a model client exists, any run row is written, or
anything is spent. Watch shell quoting; `.env.example` ships `dry-run`, so arm
inline rather than persisting `EXECUTE` in a file.

## Run inputs

Every input is a named environment variable; there is no positional argument
parsing and no inferred default for anything deciding which calls are audited.

| Variable | Req. | Meaning |
| --- | --- | --- |
| `KAUDIT_CALL_AUDIT_BATCH_MODE` | yes | Arming gate; exactly `EXECUTE`. |
| `OPENAI_API_KEY` | yes | Model credential, from the secret manager. |
| `KAUDIT_CALL_AUDIT_RUN_TYPE` | yes | One of `daily`, `monthly`, `quarterly`, `yearly`, `manual`, `test`, `backfill`. |
| `KAUDIT_CALL_AUDIT_PERIOD_START` | yes | Calendar period start, inclusive. |
| `KAUDIT_CALL_AUDIT_PERIOD_END_EXCLUSIVE` | yes | Calendar period end, exclusive. |
| `KAUDIT_CALL_AUDIT_SOURCE_START` | yes | Source scan window start, inclusive. |
| `KAUDIT_CALL_AUDIT_SOURCE_END_EXCLUSIVE` | yes | Source scan window end, exclusive. |
| `KAUDIT_CALL_AUDIT_IDEMPOTENCY_KEY` | yes | Stable run key; never generated by the CLI. |
| `KAUDIT_CALL_AUDIT_PERIOD_TIMEZONE` | no | Calendar zone label recorded on the run. Defaults to `Asia/Kolkata`. Stored, never used to convert. |
| `KAUDIT_CALL_AUDIT_BATCH_SIZE` | no | Rows per source page. Defaults to `25`. |
| `KAUDIT_CALL_AUDIT_MAX_PAGES` | no | Stop after this many pages. Unset reads to exhaustion. |
| `KAUDIT_CALL_AUDIT_MAX_CANDIDATES` | no | Stop after this many processed candidates. Unset means no ceiling. |
| `KAUDIT_CALL_AUDIT_CORRELATION_ID` | no | Provenance recorded on the run row. |
| `KAUDIT_CALL_AUDIT_TRIGGERED_BY` | no | Provenance recorded on the run row: a `kaudit_user.id`, not a name, handle, or email. Omit for a run with no such actor. |

Anything not listed above is not read. Do not invent settings.

## Period versus source window

- **Calendar period** (`PERIOD_START` / `PERIOD_END_EXCLUSIVE`) is what the run
  *records*, interpreted in `PERIOD_TIMEZONE` and stored exactly as written.
- **Source window** (`SOURCE_START` / `SOURCE_END_EXCLUSIVE`) is what is
  actually *scanned*, in the source's **UTC-naive** form.

Both use `YYYY-MM-DD HH:MM:SS` and are **half-open** (start inclusive, end
exclusive); a trailing `Z` or numeric offset is rejected, not converted.

**The CLI performs no timezone conversion.** Translating a calendar period into
UTC-naive source boundaries is the operator's decision, made before the run and
checked in preflight; a wrong window is expensive and hard to notice later.

## Idempotency key

Choose it deliberately and keep it stable for the run it names: a descriptive, human-checkable,
non-random string derived from run type and period — for example the shape
`callaudit-<runtype>-<period-label>-<attempt-label>`. Do not reuse a key from another
environment or generate one per invocation.

- Run identity is `(rule version, run type, period, timezone, key)`. Re-running with
  the same key and identical run identity **does not create a second run**.
- The same key describing a *different* period, rule version, run type, or
  timezone is a conflict and is refused.
- A run already claimed or settled does not advance again, and such a replay is not a success
  path: the invocation **refuses lifecycle progression before any candidate is selected or
  processed and before any model call**, then reports a bounded lifecycle/failure code. Do not
  assume a specific one — `CALL_AUDIT_RUN_CLAIM_FAILED` is one outcome; recording that terminal
  failure against an already-settled run can surface another bounded run code instead.
- Results are append-only, keyed per run and source reference, so a re-issued key
  cannot write duplicate result rows or pay to re-process candidates.

## Command template

Arm inline. `OPENAI_API_KEY` is deliberately **absent** below — it must already be in
the invoking process environment, injected by the approved secret manager or runtime.
```bash
# OPENAI_API_KEY is pre-injected into this environment. Never assign, fetch, or echo it here.
KAUDIT_CALL_AUDIT_BATCH_MODE=EXECUTE \
KAUDIT_CALL_AUDIT_RUN_TYPE=test \
KAUDIT_CALL_AUDIT_PERIOD_START='YYYY-MM-DD 00:00:00' \
KAUDIT_CALL_AUDIT_PERIOD_END_EXCLUSIVE='YYYY-MM-DD 00:00:00' \
KAUDIT_CALL_AUDIT_PERIOD_TIMEZONE='Asia/Kolkata' \
KAUDIT_CALL_AUDIT_SOURCE_START='YYYY-MM-DD HH:MM:SS' \
KAUDIT_CALL_AUDIT_SOURCE_END_EXCLUSIVE='YYYY-MM-DD HH:MM:SS' \
KAUDIT_CALL_AUDIT_IDEMPOTENCY_KEY='<STABLE_RUN_KEY>' \
KAUDIT_CALL_AUDIT_BATCH_SIZE=5 \
KAUDIT_CALL_AUDIT_MAX_PAGES=1 \
KAUDIT_CALL_AUDIT_MAX_CANDIDATES=5 \
KAUDIT_CALL_AUDIT_TRIGGERED_BY='<KAUDIT_USER_ID>' \
npm run callaudit:batch
```
Every angle-bracket token is a placeholder. Do not commit a filled-in version.

## Shadow-first sizing

1. First run: set `MAX_CANDIDATES` and `MAX_PAGES` so at most a handful of
   candidates are processed, as in the template above.
2. Review the summary and sanitized report with the run owner and the reviewer
   named in the approval.
3. Raise the ceilings one step at a time, only after explicit written agreement.
   Clearing both ceilings reads the period to exhaustion; never on a first run.

## Preflight checks

- [ ] Exactly one rule version is `active`, and it is the intended one.
- [ ] The MySQL account has `SELECT`-only on the source table (verify the grant,
      not the intent) and no DDL rights.
- [ ] `0008_call_audit_foundation.sql` applied here and the schema matches.
- [ ] Calendar period boundaries and their UTC-naive source-window counterparts
      computed and independently checked by a second person.
- [ ] Candidate ceiling, expected model spend, and its approval recorded.
- [ ] `KAUDIT_CALL_AUDIT_BATCH_MODE` is not persisted as `EXECUTE` in any file, and the named operator is present and owns the run.

## Success verification

Use only privacy-safe surfaces:

1. Exit code `0`, plus the single stdout summary line — an allowlist of ids,
   closed enum values, bounded codes, and counts: `runId`, `runCreateOutcome`,
   `terminalStatus`, `failureCode`, `stopReason`, `pagesRead`,
   `candidatesSelected`, `candidatesProcessed`, `counts` (`processedTotal`,
   `succeededTotal`, `failedTotal`, `skippedTotal`, `operationalOnlyTotal`,
   `contentAuditedTotal`).
2. Check `stopReason`: `exhausted` means the window was fully read;
   `page_limit` / `candidate_limit` mean a ceiling stopped the run early and the
   period is only partly audited.
3. Confirm `candidatesProcessed` is within the approved ceiling and `failedTotal`
   matches what the reviewer expects.
4. For aggregate review use the sanitized Call Audit reporting surface
   (`/call-audit` on the secure dashboard, via `/api/v1/call-audit/report`).

**Never** print, query, export, or paste raw transcripts, business or compiled
prompts, raw model responses, provider error prose, lead identity, Task IDs, or
any source free text. If a question cannot be answered from run status, counters,
or sanitized reporting, escalate instead of querying raw data.

## Failure handling

- Failures print on stderr as bounded uppercase machine codes with at most the
  *name* of the offending input variable — never its value:
  `CALL_AUDIT_BATCH_MODE_NOT_EXECUTE`, `..._MISSING_INPUT`, `..._INVALID_INPUT`,
  `..._CONFIG_UNAVAILABLE`, `..._RULE_READ_FAILED`, `..._NO_ACTIVE_RULE`,
  `..._ACTIVE_RULE_DETAIL_MISSING`, `..._MODEL_NOT_CONFIGURED`,
  `..._MODEL_INIT_FAILED`, `..._RUN_NOT_SETTLED`, `..._UNEXPECTED_FAILURE`, plus
  run-phase codes such as `CALL_AUDIT_RUN_SOURCE_READ_FAILED` and
  `CALL_AUDIT_RUN_CANDIDATE_FAILED`.
- Triage from the code alone. It names a stage, safe to quote in a ticket; the
  underlying fault is deliberately not surfaced.
- **Preserve the idempotency key.** Minting a new key to get past a failure
  creates a second run over the same period and pays for it again.
- **No blind retries.** A settled run refuses re-claim by design. Fix the named
  cause (input, grant, active rule, credential, connectivity), then decide with
  the run owner whether a new, deliberately keyed run is warranted.
- The pool closes automatically on both paths; nothing to clean up manually.

## Stop and rollback

No process to kill and nothing to drain: stopping means **stopping further
invocations**. If anything looks wrong:

1. Stop issuing the command; notify the run owner and the reviewer.
2. Do **not** delete or edit run rows, source references, results, metric
   scores, or usage events. Call Audit persistence is append-only and is the
   evidence of what happened.
3. Investigate using run status, counters, and sanitized reporting only.
4. If audits ran under a wrong contract, the correction is an administrator
   retiring/replacing the rule version plus a later, deliberately keyed
   re-audit — not deletion.

Migration rollback and destructive SQL are **out of scope** and need a separate
approved plan.

## Production promotion checklist

None of the following is claimed to be implemented today. Each is a gate to be
met and evidenced before any production Call Audit batch is considered:

- [ ] OIDC-backed administrator identity for rule-version creation/activation.
- [ ] Production infrastructure defined: secret management, MySQL TLS, least-privilege account, supervised execution host.
- [ ] Monitoring and alerting on run terminal status, failure codes, counters.
- [ ] Backup/restore evidence for the production database, signed off by the named data owner.
- [ ] Retention policy for run, result, and usage-event data approved.
- [ ] Staging shadow runs accepted in writing by the reviewer, with sizing history from small ceilings upward.
- [ ] Model cost approved against projected production candidate volume.
- [ ] `0008_call_audit_foundation.sql` applied to production as an approved, supervised operation.
